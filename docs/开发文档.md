本文档描述了项目的开发目的等内容。

实现一个RTSP回放录制服务端，使用Minimal API+react+typescript实现一个前端页面。用户双击可执行程序后，提示用户访问前端页面。

可以禁用国际化，以NativeAOT友好为目标。

技术栈：
- 后端：.NET 10 Minimal API
- 前端：react + typescript。
- 实时通信：WebSocket
- 编译目标： 必须支持 NativeAOT (Ahead-of-Time) 编译。这意味着：
    - 禁止使用 `Newtonsoft.Json`，必须使用 `System.Text.Json` 并配合 Source Generator。
    - 避免使用严重依赖运行时反射的第三方库。

#### 主页面（任务管理页面）
表格列：频道ID、频道名称、起始时间、结束时间、录制进度条、已录制大小(KB/MB/GB自动计算)、录制状态（正在录制/等待录制/已完成/失败等，需要用不同颜色表示）、操作按钮（开始录制/停止录制）。

- 列： 频道ID | 频道名称 | 计划开始时间 | 计划结束时间 | 进度条 | 已录大小(动态更新) | 状态 | 操作

- 任务列表按“正在录制 / 已完成录制”分 Tab，等待中归入正在录制，失败和已停止归入已完成；列表默认每页 20 条，支持翻页。
- 支持勾选任务后批量停止录制或删除记录；等待中任务可批量取消，正在录制的任务需先停止再删除。
- 进度条： 根据 (当前时间 - 开始时间) / 总时长 计算。
- 操作按钮：
    - 录制中：[停止录制]
    - 已结束：[查看Info] [下载] [删除]
- 交互逻辑：
    -查看Info： 后端调用 mediainfo 命令行（假设环境已安装）或使用 FFmpeg 库获取视频元数据，弹窗显示。
    -下载： 浏览器直接流式下载生成的文件。
    -删除： 二次确认后，仅删除数据库中的任务记录，不物理删除文件。

#### 新建录制任务 (Modal弹窗)
- 字段：
    - 选择频道 (下拉框)

### 直播录制（udpxy / RTP / UDP）

- 频道 URL 支持 udpxy HTTP 单播地址：`http://.../rtp/组播地址:端口`、`http://.../udp/组播地址:端口`。
- 频道 URL 也支持直接组播：`rtp://组播地址:端口`（RTP 封装的 MPEG-TS）和 `udp://@组播地址:端口`（裸 MPEG-TS）。多网卡环境可在地址后追加 `?localaddr=本机IPv4地址` 指定接收网卡。
- 直接 `rtp://` 会剥离 RTP 头（含 CSRC、扩展和 padding），`udp://` 按原始 MPEG-TS 数据报写入；两者都会送入 TS 实时检测。
- `rtp://` 使用约 80ms 的 RTP 序列重排窗口（上限 512 包），支持乱序恢复、重复包丢弃和序列号回绕；SSRC 变化（如前端重启）时先写出旧流缓冲再重置重排状态。`udp://` 没有序列号，无法可靠重排，真实丢包仍会体现在 TS 连续性检测中。
- 同端口频道共享一个 UDP 接收 socket，按订阅快照以目标组播组分发到各任务的有界队列（8192 数据报）；队列积压时会丢弃并记录警告，避免磁盘抖动直接阻塞系统收包。组播成员每 60 秒刷新一次；瞬时 socket 错误只重试不终结同端口录制；Windows 上禁用 ICMP 不可达触发的连接重置。
- 每次接收开始时记录 UDP 来源地址、RTP SSRC 和初始序列，来源地址中途变化会记录告警，便于区分主备组播源（如直连异常但 udpxy 正常时）。
- 程序根据 URL 自动识别直播源；直播任务不追加 `playseek`、`starttime` 等回放参数。
- 直播任务严格按预约的开始时间启动；开始时间已过但结束时间未到时立即补录；两者都已过时标记失败。
- 直播任务的默认文件名只包含频道和开始时间，不写入可能被修改的结束时间；回放任务保留起止时间。
- 直播按墙钟结束时间由调度器停止，不执行“PCR 实际时长不足 60 秒判失败”的校验。
- 待录制或录制中的直播任务可以修改结束时间；延长继续写入同一文件，缩短按新时间停止。调度器触发的结束记为已完成，手动停止记为已停止。修改结束时间不会重命名已有文件。
- 服务重启时，之前残留的 Recording 任务会标记为失败（服务重启中断），不会继续显示为录制中。
- 30 秒无数据判定断流并自动重新加入（退避 2~10 秒，最多 5 次），继续写入同一文件，超出恢复预算才判失败；若持续收到非 MPEG-TS 数据，5 秒后判定失败。Windows 需允许程序接收 UDP 入站流量。

### TS 实时检测

- 录制写入的 TS 字节会同步送入增量检测器，进度通过 WebSocket 推送到任务表。
- 检测项包括 TS 同步、传输错误、连续计数、PAT/PMT 完整性、PES 长度、PCR/PTS/DTS、音画漂移和 PID 统计。
- 任务表“TS 检测”列显示正常/警告/异常、视频/音频编解码器和错误/警告数量；悬停显示缩略摘要，点击（手机端点按卡片）打开详情弹窗，查看完整扫描结果：码率、包数、扫描大小、PID 数、全部音视频轨、最早几条异常事件（同时显示本地时间与相对录制开始的 0-based 时刻；同级别同类型且 3 秒内的异常会合并并显示 ×次数，跨 PID 合并为“N 个 PID”，`*` 为估算时刻）与最近事件。录制中的任务也可打开，弹窗随 WebSocket 推送实时刷新。
- 检测为封装层和时间轴检查，不解码视频画面；当前支持 188 字节 TS。
- 码率按 SI 换算（1 kbps = 1000 bit/s，与 ffmpeg/MediaInfo 一致）；文件大小按 1024 进制显示。
- 检测器核心逻辑复用自同作者的 [TSCutter.GUI](https://github.com/nilaoda/TSCutter.GUI)。

### 录制日志

- 默认在录像文件旁生成同基名的 `.log`，例如 `Live_xxx.ts` 对应 `Live_xxx.log`。
- 日志记录任务信息、实际开始时间、URL、异常和最终状态；仅在 TS 检测出现错误或警告且状态发生变化时追加摘要，不记录常规进度。
- `recsettings.json` 的 `writeRecordingLog` 或应用配置页开关可关闭日志；关闭后仅影响之后启动的录制。
- `.log` 文件不会出现在“录制管理”列表中。

### 实时错误日志面板
任务管理页面底部固定一个可收起的错误面板，数据来自后端进程内环形缓冲（默认 10000 条，可在设置页调整为 100–50000 条，约 5 秒内生效；服务重启清空）：

- 写入：录制进度中 TS 检测的 `lastEvent` 变化（按错误/警告数量增量分级）与任务失败原因；同一任务、同一异常身份且 3 秒内只更新最后一条的次数/时间，避免刷屏；失败消息只记录一次。
- 接口：`GET /api/task-errors` 返回快照与 `generation`，`DELETE /api/task-errors` 清空（代次递增）；WebSocket 新增 `taskErrorLog` 增量消息（带 revision），断线重连后前端重新拉快照合并。
- 面板：任务管理页面底部可见，默认收起；展开后拖动上沿调整高度（140px–50vh，高度记 localStorage），按任务分组（任务名 + 频道/文件名），组可折叠，错误红/警告黄/正常绿；录制中且无异常的任务显示绿色“暂无异常”，已完成且无异常的隐藏；组内最新在上，消息不换行；清空会同步到所有已打开页面。

### 频道批量编辑 API

供脚本定期刷新频道地址等使用：`POST /api/channels/bulk-edit`

```json
{
  "channels": [
    { "id": 0, "url": "http://example.com/stream/1" },
```

### 频道检测
- 频道列表支持单条和批量检测；每次采样约 5 秒，采用内存流式检测，不写入录像文件。
- 批量检测按并行数量分批执行，结果逐批刷新并显示“检测中 X/Y”；未开始的频道不会显示为检测中。检测过程中可随时停止，单批超时会自动终止。
- 检测设置可调整并行数量（1-10，默认 3）和失败重试次数（0-5，默认 0），仅对不可访问的频道重试，设置保存在当前浏览器。
- 检测完成后可一键移除全部失效频道（需二次确认；正在检测或存在未保存修改的频道不会列入）。
- 检测结果包括可访问性、全部视频轨和音频轨编码、实时码率和探测耗时；详情弹窗展示尝试次数。TS 错误/警告等录制质量信息只在录制任务的检测详情中展示。
- 最近一次成功检测的编码、码率和检测时间会保存到程序目录下的 `channel-profiles.json`，服务重启后仍会显示上次结果；频道 URL 修改或频道删除时自动失效。本次检测的失败状态仍只保留在进程内。
- 任务与定时规则的频道下拉显示视频/音频编码和码率（如 `H.264 / AAC · 7.9 Mbps`），支持按编码搜索；没有档案时显示“未检测编码”。
- 详情弹窗展示全部轨道和失败原因；RTP/UDP 失败时提示检查组播、防火墙和 `localaddr`。
- 分辨率暂未从 TS 解析。

## 实现细节
1. 后台调度器： 实现一个 `BackgroundService`，每秒轮询一次。检查是否有 Pending 任务到达开始时间。如果当前并发数 < `maxRecordingTasks`，则开始录制。
2. 日志： 同时要求console/file输出，输出录制开始、停止、错误信息。每天一个日志文件自动处理。保存文件夹为程序运行路径下的logs文件夹。
3. 获取运行文件夹：同时考虑dotnet dll启动和直接运行可执行文件的情况。
4. 未来的时间：如果用户输入了一个未来的时间，而当前时间还未到该时间，那么就等待到该时间再开始录制。同时为了避免回放内容还没有生成，此类情况需要等待一会儿再开始录制。
